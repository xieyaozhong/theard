AI COMMERCE AUTOMATION / SYSTEM VIEW

把「自動發文」
拆成一套可以理解的系統

這不是一支按下去就發文的腳本，而是一條從商品資料、圖片、聯盟連結、選品、Preview、Dry Run、Human Gate 到 Publisher 的完整工作流。這個頁面把整套流程架構化，讓非工程背景的人也能看懂「資料怎麼流、程式怎麼判斷、什麼時候可以做、什麼時候必須停」。

01 / SYSTEM MAP

十段式架構

越靠近 Publisher，資料要求越嚴格。點擊任一模組，可以展開它在整套系統中的責任。

02 / THREE LAYERS

三層控制模型

DATA

資料層

商品、圖片、主題、聯盟短連結、發文歷史與 Publisher 狀態。這一層的目標是建立「單一事實來源」。

  • products.json
  • images.json
  • topics.json
  • post-history.json
  • publisher-state.json
DECISION

決策層

選題、選品、評分、相關性、文案與組合多樣性。AI 可以提出候選，但不能自己證明資料是真的。

  • Scoring
  • Product Agent
  • Smart Selection
  • Content rules
ACTION

執行層

Preview、Dry Run、Human Gate、Threads API、Registry 與 Recovery。這一層開始產生外部影響，所以需要最嚴格的控制。

  • Preview
  • Dry Run
  • Publisher
  • Checkpoint
03 / HOW IT ACTUALLY WORKS

一篇貼文，實際上怎麼跑完？

以 Daily Production 為起點，從磁碟上的 JSON 一路追蹤到可以被 Threads Publisher 使用的 Preview。

STEP 01

讀取資料

Python 讀取 topics.json、images.json、products.json 與 config。這一層不是 AI 猜測，而是 deterministic data loading。

INPUT → JSON
OUTPUT → Python dict
STEP 02

驗證圖片

程式確認檔案存在、大小不為 0，並真正使用影像函式庫打開檔案驗證。壞圖不會進入後續流程。

valid_file()
TRUE / FALSE
STEP 03

取得主題

只取 active=true 的主題，再依 priority 與 id 排序。內容策略被存成資料，而不是藏在某個人的腦中。

topics.json
→ ordered topics
STEP 04

Product Agent 選品

先排除 Eligibility 不通過、低於最低分數與主題無關的商品，再依 relevance、score、freshness、usage frequency 排序，最多取 4 個。

topic + products
→ selected 4
STEP 05

Quality Gate

再檢查是否剛好 4 商品、每個商品都有有效圖片、affiliate_short_url 格式正確。有任何 issue，該主題就 SKIPPED。

PASS → continue
FAIL → SKIP
STEP 06

生成 Preview

寫出 Topic、Caption、Products、Selection reason、Images 與 Threads Reply。這份 Markdown 同時給人審核，也給 Publisher 解析。

preview/daily/
post-001.md
STEP 07

Dry Run

重新解析 Preview，檢查 4 商品、4 圖、4 個留言連結與缺圖狀態；不接 API、不登入、不修改 JSON。

can_publish
TRUE / FALSE
STEP 08

Human Gate

人確認品牌、圖片、商品與連結，才允許從「內部資產」跨到「外部行為」。

APPROVE
or STOP
STEP 09

Publisher

讀取 .env / environment，建立 media container，再呼叫 publish endpoint。只有 2xx 且回傳 id 才視為成功。

creation_id
→ publish_id
STEP 10

Registry / Recovery

把 publish_id、reply 狀態、content hash 與 checkpoint 寫回狀態。下次重跑同內容時可以辨識 ALREADY_COMPLETED。

DONE / FAILED
PENDING
04 / ELIGIBILITY GATE

AI 不能自己相信自己

系統不問「這商品看起來不錯嗎？」而是問「它是否滿足所有可驗證條件？」

候選商品

  • 可能有商品名稱
  • 可能有來源頁
  • 可能缺官方短連結
  • 可能沒有可信圖片
  • 可能與主題不相關
→

READY 商品

  • active = true
  • 必要欄位完整
  • 官方 affiliate short URL
  • 可信且可讀的圖片
  • 分數達門檻

06 / FILE MAP

第一次打開 Repo，先認這些檔案

data/products.json

商品事實。Product ID、title、category、URL、affiliate_short_url 等。

data/images.json

圖片事實。把 image_id 與 product_id、實體檔案關聯起來。

data/topics.json

主題池。active 與 priority 控制每天可用內容方向。

agents/product_agent.py

主題相關性、Scoring、Eligibility 與候選排序。

scripts/daily_production.py

每日候選生產入口。生成最多 3 篇，每篇要求 4 商品。

preview/daily/

人類審核介面，也是 Publisher 的輸入 contract。

scripts/threads_publisher_dry_run.py

發布前稽核。不產生外部副作用。

scripts/threads_publisher.py

讀設定、Parse Preview、Create Container、Publish。

07 / FAILURE PATH

可靠系統不是只畫成功路徑

DATA FAIL

資料不足

商品不足、缺圖、沒有官方短連結。

→ BLOCK / SKIPPED

CONFIG FAIL

設定問題

缺 THREADS_ACCESS_TOKEN、USER_ID 或 API_BASE_URL。

→ ConfigError

API FAIL

外部服務問題

HTTP error、timeout、非 JSON response、權限或驗證問題。

→ STOP / RECOVER
